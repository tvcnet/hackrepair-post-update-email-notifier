## Confirmed findings

### P1 — A failed continuation schedule strands background recipients

`includes/class-pue-delivery.php:177-188` persists the next offset and calls `wp_schedule_single_event()`, but ignores its return value. When scheduling fails, the job remains queued with no callback to finish it. There is no independent job sweep/recovery hook in this implementation.

Reproduced in an isolated fault-injection harness loading the real delivery class: 21 recipients, batch size 20, mail stub accepts all, continuation scheduler returns false. Result: 20 sent, offset 20 persisted, one recipient remains, zero scheduled callbacks. No real mail, database or cron was used.

Required: handle scheduling failures explicitly, surface a failed/paused job state, and provide a bounded recovery mechanism. Add tests for false and WP_Error results, logging disabled, and a failed continuation after at least one successful batch. Do not silently resend already accepted recipients.

### P1 — A transport exception leaves the job locked without recovery

`includes/class-pue-delivery.php:152-174` takes the job lock and sends the batch without exception-safe lock release or per-recipient progress persistence. `send_one()` clears its plaintext state in finally, but exceptions still escape to the worker. An exception or process interruption after partial sending can leave a stale cursor and a lock; blindly retrying the old cursor can duplicate sends.

Reproduced with an injected RuntimeException from the mail stub: the lock remains, cursor is unchanged, no recovery callback is scheduled. This is distinct from normal `wp_mail() === false`, which the happy-path tests cover.

Required: exception-safe worker cleanup, explicit handling of uncertain/partial progress, retry/failure policy and tests. Re-read the job after acquiring its lock; the current pre-lock snapshot can be stale under overlapping workers. Test simultaneous callbacks, lock expiry, transport exceptions, deactivation/reactivation with queued jobs, and bounded retry behavior. Exactly-once delivery cannot be promised across an SMTP acceptance followed by a process crash; document that boundary.

### P2 — Site Health can report unrelated sender domains as matching

`includes/class-pue-site-health.php:80-97` approximates a registrable domain using its last two labels. Thus unrelated `client.co.uk` and `unrelated.co.uk` both become `co.uk`.

Reproduced by invoking the actual Site Health callback with site `https://client.co.uk` and sender `sender@unrelated.co.uk`: status good, label "Post update email sender matches the site domain".

Required: a conservative exact/subdomain comparison, or a maintained public-suffix-aware approach, with tests for multi-label suffixes, subdomains and unrelated domains. Describe the check as address/domain consistency; it does not validate SPF, DKIM, DMARC, actual mail transport or delivery.

- Per-recipient durable checkpoints, fenced SQL writes tied to atomic leases, fresh option reads after acquiring the lease, and exception-safe ownership-aware cleanup. A crashed/uncertain transport is not replayed automatically.
